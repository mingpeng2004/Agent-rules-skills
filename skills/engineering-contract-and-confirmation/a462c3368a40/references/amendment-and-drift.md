# 修订、版本绑定与漂移检查

## 一、新需求怎么分类

| 类型 | 判据 | 处理 |
|---|---|---|
| 契约修订 | 改动已确认域：框架、安全、数据、接口、验收、质量标准 | 用户明确确认，无超时 |
| 偏好修订 | 域内细节：命名、文案、局部样式、参数取值 | 通知后 300 秒默认 |

拿不准就按契约修订处理。宁可多问一次，不要静默改掉已确认的东西。

## 二、修订提案要带的东西

```json
{
  "amendment_id": "amend_001",
  "kind": "contract",
  "summary": "一句话说明新需求与为什么",
  "sections": { "architecture": { "decision": "新的确定结论", "rationale": "依据" } },
  "impact": "对用户/数据/接口/安全/运维的影响",
  "rollback": "如何退回上一版本",
  "fact_sources": ["支撑该修订的实际文件"],
  "affected_tasks": ["受影响的既有任务"]
}
```

`fact_sources` 必须是真实存在的文件；提案会被快照并记录哈希。

## 三、应用后的版本效应

- 契约版本 +1，变更前后的取值一并记入历史
- 触及域的任务自动判为 stale：check 退出码 2，阻断执行，直到重新对齐
- 未触及域的任务不受影响

这正是"迭代但不跑偏"的机制：新需求落地后，只有真正相关的工作被拦下。

## 四、漂移检查放在哪

三个点，缺一不可：

1. **Unit 边界**：每做完一个可验证单元
2. **恢复点**：会话中断后恢复时
3. **契约相关动作前**：任何会受契约约束的改动之前

命令（AgentOS 提供）：

    bin/AgentOS.ps1 -Command contract-check -ProjectRoot <project>
    bin/AgentOS-Contract.ps1 -Command status  -ProjectRoot <project>

`check` 成功退出码 0，阻断时退出码 2。

## 五、容易踩的坑

- **只改代码不改契约**：需求变了但契约没动，检查照样通过，意图已经丢了
- **把历史任务当成阻塞**：老任务没有版本绑定属于正常，只提示不阻断
- **提案快照被改**：修订快照哈希失配后该修订失效，必须重新提案，不要绕过
- **用修订做范围蔓延**：一个需求一个修订，不要把不相关改动打包
- **确认后不复查**：契约封版不等于冻结，安全或数据相关的域要定期回看是否仍成立

## 六、和证据的关系

契约决定"做成什么样算对"，证据决定"这次真的做到了没有"。两者都要：

- 依赖框架意图的声明，在证据账本里记录它对应的契约版本
- 契约变了，受影响的旧证据按账本规则作废或重验，不要继续引用
