# 界面与交互一致性

## 一、把参考当方法，不当依赖

| 参考类型 | 用途 | 边界 |
|---|---|---|
| 真实产品库 | 研究信息架构与真实用户流程 | 不搬运截图或专有界面 |
| 灵感画廊 | 方向未定时的气质参考 | 不照搬布局与品牌 |
| 设计系统 / DESIGN.md | 提取令牌结构、组件词汇、命名纪律 | 遵守许可，记录来源 |
| 模式与检查清单库 | 把交互规则变成验证项 | 按项目约束改造后再用 |

不把外部站点、字体、图标包接进产品路径；采纳需记录来源与许可；默认禁止网络抓取参考资源。

## 二、先有契约，再有界面

界面漂移最常见的根因是跳过"建契约"这一步：没有令牌和组件清单，每个页面自己发明间距和颜色。

项目应持有两件工件：

- **DESIGN.md** —— 设计原则、信息架构、交互模型、组件清单、状态、可访问性目标、设备约束、改动路径
- **design-tokens.json** —— 颜色、字体、间距、圆角、层级、动效的机器可读取值；代码读它，散文不复述数值

外部设计系统可以作为**结构蓝本**，但必须改写成本项目的上下文与硬件约束，并记录许可。

## 三、五阶段与产出物

| 阶段 | 目标 | 产出 |
|---|---|---|
| 定方向 | 定气质、密度、对比、动效策略、目标环境 | 方向说明 |
| 拆产品 | 理清真实流程 | 界面清单与关键路径流程图 |
| 建契约 | 冻结语言 | DESIGN.md + design-tokens.json（版本化登记） |
| 抠细节 | 组件与状态 | 组件规格 + 模式清单核对结果 |
| 落地 | 映射到真实框架与硬件 | 实现与约束映射说明 |

## 四、一致性检查（可交给验证者逐条打勾）

- 所有界面只用令牌，视图层无硬编码颜色/尺寸/间距
- 组件清单完整：默认/悬停/按下/禁用/聚焦/错误态按需定义
- 文本在目标尺寸下不溢出、不重叠、不静默截断
- 加载态、空态、错误态、长内容态下布局稳定
- 同一动作在不同页面行为一致；破坏性操作可辨识且尽量可撤销
- 对比度、焦点顺序、标签、输入方式可达性符合目标设备
- 术语与产品目标一致，无重复概念
- 图标来自同一图标库，线宽与尺寸统一

## 五、嵌入式与受限设备的额外约束

界面设计前先写清：屏幕尺寸与方向、可用内存与刷新帧预算、输入方式（触摸/旋钮/按键）、
显示驱动限制、界面运行在 MCU / RTOS 任务 / 配套 PC / 浏览器。

做法：先用设计工具或令牌优先的方式规划界面，再映射到实际控件框架；桌面或 Web 设计系统
只提供视觉语言，组件实现必须服从硬件约束。令牌文件是唯一事实源，映射步骤因此可复核。

## 六、改动分级

- 令牌内的间距、文案、局部取值 → 偏好修订（300 秒默认）
- 令牌刻度、组件结构、交互模型变更 → 契约修订（明确确认，版本递增）

## 七、不要过度承诺

本方法不能自动渲染、不能自动判定审美，也不能证明"符合某设计系统"。
视觉类结论需要人工或截图复核，并如实标注为人工复核。
