# 停止代码（Bugcheck）码表与判读

> **纪律 H2：只登记语义已确认的码。未登记的一律 `UNKNOWN`，绝不猜测。**
> 把未知码输出成某个名字，比输出 `UNKNOWN` 危害大得多——
> 它会让读者以为已经知道原因了。

---

## 1. 读码来源的优先级

| 来源 | 权威性 | 说明 |
|---|---|---|
| **41 事件的 `BugcheckCode`** | ★★★ 最高 | 唯一在**每次**崩溃都写入的来源 |
| BugCheck 1001（Application） | ★★ | **转储失败时可能完全缺失** |
| `MEMORY.DMP` / Minidump | ★ | 需要转储成功才有 |

**永远从 41 事件读。** 1001 缺失不代表没蓝屏。

---

## 2. 码表

### 2.1 内存 / 页损坏族

| 码 | 名称 | 要点 |
|---|---|---|
| `0x50` | PAGE_FAULT_IN_NONPAGED_AREA | 非分页区访问违例；常见于内存破坏或驱动野指针 |
| `0x1A` | MEMORY_MANAGEMENT | 内核堆管理结构被破坏 |
| `0x12B` | **FAULTY_HARDWARE_CORRUPTED_PAGE** | 字面即「硬件损坏页」——**硬件嫌疑的直接证据** |
| `0x139` | LIST_ENTRY_CORRUPTION | 内核链表被破坏，常见于并发/内存问题 |

### 2.2 驱动 / 执行体族

| 码 | 名称 | 要点 |
|---|---|---|
| `0xD1` | DRIVER_IRQL_NOT_LESS_OR_EQUAL | 驱动在过高 IRQL 访问分页内存 |
| `0x7E` | SYSTEM_THREAD_EXCEPTION_NOT_HANDLED | 系统线程未处理异常 |
| `0x3B` | SYSTEM_SERVICE_EXCEPTION | 系统服务例程异常，`P1` 常为 `0xC0000005` |
| `0x9F` | DRIVER_POWER_STATE_FAILURE | **电源状态迁移**中的驱动问题 |
| `0x154` | UNEXPECTED_STORE_EXCEPTION | 意外存储异常 |
| `0xA0` | INTERNAL_POWER_ERROR | 内部电源错误（与休眠/唤醒相关） |

### 2.3 显示 / TDR 族

| 码 | 名称 | 要点 |
|---|---|---|
| `0x116` | VIDEO_TDR_TIMEOUT | 视频引擎超时 |
| `0x117` | VIDEO_TDR_TIMEOUT_DETECTED | 检出显示超时 |
| `0x119` | **VIDEO_TDR_FAILURE** | 显卡/显示驱动无响应 |
| `0x141` | VIDEO_ENGINE_TIMEOUT_DETECTED | 显示引擎超时 |

**TDR 族的排查方向**：显示驱动版本、**虚拟显示适配器**、远控/串流软件、
GPU 供电与温度、现代待机下的电源状态迁移。

> 2026-10-15：`0x119` 曾因**不在码表**而落 `UNKNOWN`。
> 这不是小事——`UNKNOWN` 与 `VIDEO_TDR_FAILURE` 指向完全不同的排查路径。

### 2.4 调度 / 内核族

| 码 | 名称 | 要点 |
|---|---|---|
| `0x133` | DPC_WATCHDOG_VIOLATION | DPC 超时。**常与显示驱动相关**，但也可能是内存 |
| `0xEF` | CRITICAL_PROCESS_DIED | 关键进程死亡 |

### 2.5 无码

| 码 | 含义 | 注意 |
|---|---|---|
| `0` | **真·硬断电 / 挂死** | 仅当事件中**确实存在该节点且值为 0** 才成立 |

> **节点缺失 ≠ 值为 0。** 节点缺失说明**读不到**，归为
> `BUGCHECK_CODE_UNREADABLE`，不能贴上「硬断电」标签。
> 这是本项目已实际犯过的错（第 23 例）。

## 3. 码分布的判读

### 3.1 同一个码反复出现

倾向于**单一驱动或单一子系统**故障。
把嫌疑收敛到该码对应的路径，查驱动版本与最近变更。

### 3.2 多个不同的码（强信号）

倾向于**共同底层**：内存劣化、供电不稳、固件不稳。
多个不同码来自同一底层，是内存破坏随机性的典型表现。

实测样例（MING-SERVER-M00，6 次崩溃）：

```
0x50 → 0x12B → 0x133 → 0x3B → 0x119
五个码各不相同 → 不像五个独立故障 → 指向一个共同底层
```

### 3.3 间隔趋势比单次码更有价值

看**间隔**是否单调收短。全程平均 MTBF 会被早期的稀疏期严重拉长，
**掩盖加速信号**——必须同时给出「全样本 MTBF」与「最近 3 次 MTBF」两个数。

## 4. 硬件诊断：为什么 WHEA 安静不能排除内存

```powershell
Get-CimInstance Win32_PhysicalMemory | Select-Object Tag, Capacity, DataWidth, TotalWidth
```

| `DataWidth` / `TotalWidth` | 含义 | WHEA 可用性 |
|---|---|---|
| `64` / `64` | **非 ECC** | **没有纠错就没有上报通道，WHEA 0 条是预期行为** |
| `72` / `64` 等 | ECC | 硬件错误**应当**上报；此时 WHEA 0 条才是真异常 |

> **非 ECC 机器上「WHEA 一条没有」绝不能作为「内存没问题」的证据。**
> 这是本类问题最容易产生假排除的地方。

### 4.1 实测只能做到什么程度

| 手段 | 能否无人值守 | 限制 |
|---|---|---|
| 用户态内存筛查脚本 | 能 | 只能发现明显页错误，**不能替代**硬件诊断 |
| `mdsched`（Windows 内置） | **否** | 需**开机后有人按 Enter**，无人值守会直接跳过 |
| MemTest86 | **否** | 需**插 U 盘现场运行**，多轮数小时 |
| 逐条换内存（插槽隔离） | **否** | 需现场拆机 |

**结论**：内存硬件根因**必须安排现场**。
在拿到实测结果前，任何「内存有问题」都只能写成**候选假设**，
不得写成结论（H5/H6）。

---

## 5. 新增码的纪律

1. 语义必须**已确认**（官方文档或权威来源），不靠推测。
2. 加入码表的同时，**必须**加一条回归测试断言该码解析正确。
3. **码表改动不能让历史记录自相矛盾**——若台账只追加，
   聚合时须从 `bugcheck_dec` **重新推导**名字，而不是信任存储字段。
