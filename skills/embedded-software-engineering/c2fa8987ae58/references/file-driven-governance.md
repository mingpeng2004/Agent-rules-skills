# 文件驱动工程治理

用于非平凡开发、接管、重构、调试和跨会话工程闭环。这里定义通用文件关系；项目宪法、锁定需求、既有 SSOT 与用户当前指令优先。轻量任务复用一条现有任务/变更记录即可，不为了文档数量生成五个空文件。

## 1. 先映射，再补缺

目标不是换文件名，而是让工作受权威文件约束：

`GOALS → FRAMEWORK / contracts → DEVELOPMENT_PLAN（Phase → Task → Unit）→ ACCEPTANCE / evidence → PROJECT_STATE / checkpoint`

| 节点 | 回答的问题 | 模板 | 已有项目的优先做法 |
|---|---|---|---|
| GOALS | 为什么做、边界、可测成功是什么 | [PROJECT_GOALS.md](../assets/templates/PROJECT_GOALS.md) | 映射 north_star、需求、design_goal 或原 Word SSOT |
| FRAMEWORK / contracts | 如何划分职责、资源、接口与约束 | [FRAMEWORK.md](../assets/templates/FRAMEWORK.md) | 索引既有架构、协议、设计决策，不覆盖宪法 |
| DEVELOPMENT_PLAN | 按何种依赖推进、每步如何证明 | [DEVELOPMENT_PLAN.md](../assets/templates/DEVELOPMENT_PLAN.md) | 原任务/计划继续作为权威源 |
| ACCEPTANCE / evidence | 达到了哪些门槛、证据覆盖哪里 | [ACCEPTANCE.md](../assets/templates/ACCEPTANCE.md) | 复用验收矩阵、真实 trace 和原证据账本 |
| PROJECT_STATE / checkpoint | 当前停在哪里、下次如何安全恢复 | [PROJECT_STATE.md](../assets/templates/PROJECT_STATE.md) | 索引已有 status、task、checkpoint，不双写状态 |

先登记“逻辑角色 → 实际路径 → 权威性 → 版本/哈希 → 更新者”。同一事实只保留一个写入源；允许跨文件引用和生成快照，禁止第二套可独立修改的任务状态。已有文件足够时不复制模板。缺口必须影响当前工程决策才补；新建位置遵循项目习惯，无治理时可在已批准范围内用 `docs/engineering/<task-id>/`。

模板的 `<待填>`、示例状态和表格行都是占位，不代表事实、授权或完成。不得自动改写 AGENTS、constitution、锁定需求、用户指定的目标或验收阈值。

## 2. 目标与方案批准后的自治

先只读确认目标、现状、限制和缺失事实。把范围、设计/接口影响、Phase/Task/Unit、测量工况/阈值、风险、回退和授权边界落盘为可审阅方案。识别已经存在的有效批准；已有批准覆盖时直接引用，禁止把每个工具调用、命名或局部实现都变成重新审批。

方案批准后，自主完成授权范围内的实现、测试、构建、缺陷修复、回归、审查、文档和工程自验，并持续到门禁满足或明确的外部阻塞。任务不是“写完代码”就结束；门禁失败必须保留证据、修复根因并重验。依项目升级协议控制重复失败。

普通取舍按现有授权判断；只有项目明确设定的偏好委托才使用其实际通知和计时规则。安全、缺失事实、未知风险、锁定 SSOT、宿主审批和真实用户验收不能因沉默而通过。范围/目标/验收变化只重规划受影响部分，继续独立工作。烧录、初始化、运动等另行核对已有明确授权及现场前置，目标批准不自动扩展动作权限。

## 3. 可执行计划与可测门禁

沿用项目现有 ID，让每个目标可追踪到契约、Unit、验收条目与证据。Unit 包含前置依赖、单一结果、执行边界、通过条件/方法、证据位置与恢复；不要求猜测所有命令。只在职责、依赖或验收发生变化时调整剩余计划。

每个必需门禁注明：来源、指标/单位、适用版本配置、工况/区间/方向、阈值、验证方法、证据层级与新鲜度。无依据的阈值保持 unknown，不通过放宽阈值收口。软件适用门禁包括正常/异常/边界回归、构建、接口兼容、安全与治理检查；实时/精度/长期运行按目标给出对应工况和完整区间。

分别报告工程产物、实机行为、用户/生产验收。离线测试、仿真和成功烧录不能证明物理闭环或生产接受。失败、SKIP、超时、截断、过期、冲突及未执行结果均不能记通过。缺必需实机/用户验收时工程产物可按其已验证范围交付，整体保持 `needs-user-acceptance` 或项目对应状态。

每 Unit 前写意图和前置，后写实际观察、完整输出、证据引用、未知/冲突和下一动作。恢复先读文件与新反馈，核对工作区/配置/产物变化，不重放已超时或不明状态的设备操作。证据等级和状态直接采用项目规范；无规范时按 [验证与发布](verification-release.md) 记录可核查来源，不把推测提升为事实。

## 4. Markdown 与 Word 的权威关系

默认 Markdown 是执行 SSOT，配对 DOCX 是同源审阅快照，便于人阅读、批注和分享。若用户或项目已指定 Word 为需求/契约权威源，保留原 Word SSOT：MD 仅为经核对的工作映射，记录 Word 路径、版本、哈希和抽取限制，不反向覆盖原文。

每份生成 DOCX 在可见文档控制区及 OOXML 自定义属性记录：`SourceMarkdown`（同目录源 MD 文件名）、`SourceSHA256`（源 MD 字节的 SHA256）、`SourceVersion`（文档基线版本）、`GeneratedAt`（带时区生成时间）。源 MD 改动即将 DOCX 判为 stale，旧 Word 不可用来批准新 MD。按已批准基线、重要里程碑及交接重生成，不随每轮工具调用刷新。

若 Word 被编辑，先保存批注/修订版本及来源哈希，显式比较差异并由有权者审阅合并到相应 SSOT；重新生成前说明接受/拒绝了哪些修改。不能静默覆盖回改 Word，也不能同时把 MD 和 Word 作为互不约束的双权威源。项目批准与快照必须绑定具体版本/哈希，而不是只绑定文件名。

模板配对允许的 Word 资产必须是可检查的标准 DOCX：不含宏、嵌入可执行/OLE、外部关系、主动域或外部链接；关联 MD、版本和哈希必须匹配。检查可见内容、表格、分页、页眉页脚、字体与完整性后才交付；工具生成成功不等于视觉验证成功。Word 生成能力由宿主/文档工具提供，本 Skill 不安装渲染器或隐藏执行程序。

## 5. AgentOS 与跨客户端

AgentOS 项目先读 `.agentos/project.json`，按其中的 `status_file`、`task_dir`、`checkpoint_dir`、`working_memory`、`evidence_ledger`、`decisions_dir` 等已登记字段映射状态。缺字段查导入契约，不能臆造 schema。AgentOS 的 `protocols/FILE-DRIVEN-ENGINEERING.md` 是本核心的适配入口；其证据、审批、委托和恢复规则仍在框架原有文件维护，不能复制成另一套系统。

Codex、MiniMax Code、Kimi Code 使用同一核心文件关系，发现路径、工具审批、活动循环和后台能力按 [客户端适配](client-adapters.md) 实际探测。任何客户端无法执行的验证或计时标为未执行/受限，不用措辞伪装等价能力。

## 6. 变更与记录生命周期

变更追踪目标/契约、风险/依赖、验证、兼容与回退影响，复用现有框架和计划。每Unit刷新当前投影，阶段收口检查活动索引、失效记录、引用和待验收。历史归档先分类/引用审计，保留摘要与后继；原始证据不覆写，删除不默认授权。执行门禁见 [记录生命周期](records-lifecycle.md)。

工程资源含Token、工具调用与时间：按需读取、差异更新、摘要引用和与内容/工况绑定的结论复用，避免重复规划/测试/分工；质量与证据门禁保留。预算和真实遥测写入现有计划，方法见 [Token与工程资源](token-efficiency.md)。
