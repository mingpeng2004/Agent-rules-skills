# 确认包：怎么写、怎么答

确认包是"把该问的一次问完"的工件。写得好不好，直接决定用户是花 5 分钟答完还是被迫分多次对话。

## 一、播种：先替用户把已定的都定了

动手提问前，先把项目文件读一遍。**凡是文件已经决定的域，一律登记为已确认，不许问用户。**

| 域 | 常见权威来源 |
|---|---|
| product_goal | 北极星、设计目标、需求文档 |
| scope_and_non_goals | 治理台模块划分、范围声明 |
| quality_bar | 硬规则、CI 门禁、测试基线 |
| tech_stack | 构建文件、依赖清单、工程速查表 |
| architecture | 架构文档、模块边界说明 |
| interfaces_contracts | 协议/契约文件、API 约定 |
| data_and_storage | 数据布局、存储与迁移说明 |
| ui_and_interaction | 设计语言文档、主题文件、样式规范 |
| safety_and_hardware | 安全登记册、硬件约束文档 |
| security_and_privacy | 认证模块、威胁模型、部署形态 |
| ops_and_maintenance | 运维 SOP、部署与回滚说明 |
| acceptance_and_delivery | 交付门禁、验收标准、发布流程 |

播种必须带来源。写"AGENTS.md + north_star.md"这种可核对引用，不要写"根据项目情况"。

## 二、调研：只查没文件依据的域

对真正未决的域做**实际调查**，而不是套模板。典型动作：

- 检索网络暴露：socket / requests / http / 服务注册 / 计划任务
- 检索凭据：口令模块、密钥存放位置、是否进版本库或日志
- 核对依赖：实际安装版本、有无锁定文件
- 核对写盘范围：写哪些目录、是否碰系统路径
- 核对外部调用：子进程调用点、是否用了拼接命令

**结论只能来自实际检索。** 没查到就说未知，不要写"应该没有"。

## 三、成包：每条都要可回答

每个未决域给出六要素：

1. 现状事实（附证据来源）
2. 推荐方案（为什么是它）
3. 影响面（用户、数据、接口、安全、运维）
4. 回滚方式
5. 答复方式：确认 / 修改为… / 缓议（原因）
6. 是否属于框架级（决定会不会超时默认）

包首写清楚：已播种项无需回答、沉默不等于确认框架级事项、缓议项会阻塞依赖它的任务。

## 四、把风险和确认分开

调查中发现的问题，分两类处理：

- **需要用户判断的**：列在确认包里，说明它是否改变产品行为、是否影响既有数据
  （例如：提高口令下限会影响已设定口令的用户，必须同时给出兼容策略）
- **与本次确认无关的**：登记为独立待办，不要塞进确认包制造决策疲劳

明确写一句"本轮不改动代码，风险登记为待办"，避免接手者误以为已实施。

## 五、答复之后

1. 按答复登记：确认的写来源引用；缓议的写豁免引用
2. 全域解析后 seal 契约，版本从 1 开始
3. 待办转入正式任务（含 owner、DoD、约束），不要只留在对话里
4. 复述登记结果，让用户看到"已确认什么、还剩什么"

## 六、常见坑

- 把"文件里有相关描述"当成"文件已经决定"——描述不等于约束，要看是否被锁定
- 把调查结论写成推测（"应该没有网络访问"）——必须实际检索
- 一包塞十几个问题——未决域超过 5 个，通常说明项目文档不足，先补文档
- 用沉默代替确认——框架级事项永远等明确答复
- 答完不落盘——口头确认不产生约束，下次接手者还会再问一遍
