# 工程踩坑与教训库

> 收录**真实发生过的**失误与对策，不是通识科普。
> 每条格式：**现象 → 根因 → 判定口 → 对策**。
> 判据：能复述成一条可执行的判定口才收录；纯感想不收。
> 来源以嵌入式上位机项目（STM32F407 四电机棘轮力测试台）为主，
> 已剔除项目专有数值，保留可迁移的**结构**。

## 1. 序列化往返：字段加了但行为没变，先怀疑序列化层

**现象**：给 frozen dataclass 加字段，`to_dict` 写了、`from_dict` 的
`return X(...)` **在更早一行就闭合了括号**，新字段的两段赋值落在 `return` 之后 ——
**死代码，永不执行**。表现是「改了设置回写不生效，所有守卫都通过，函数像静默 return」。

**根因**：三件事叠加
1. `to_dict` 写进 JSON、`from_dict` 永不读回 ⇒ **静默数据丢失**；
2. `save_record` 内置的自校验 `from_dict(metadata) != meta` 本该当场抛
   `ValueError("does not round-trip")`，**却被调用方的 `except Exception`
   当「落盘失败」吞掉，只留一行 `str(exc)`**；
3. 一个**平时默认关闭**的兄弟字段其实也从未往返过 —— **"默认关闭"会掩盖序列化 bug**，
   关着的时候丢不丢无所谓。

**判定口**
- 「字段加了但行为没变」→ 先独立构造一个全字段实例打一发
  `from_dict(m.to_dict()) == m`，比读业务代码快得多。
- 静默回滚类失败，日志只剩一行 `str(exc)` ⇒ **事后完全无法归因**。

**对策**
- **穷举字段往返不变式测试**（不是逐个业务用例）：
  ```python
  m = RecordMeta(**全字段都给非默认值)   # 默认值相同会掩盖漏读
  assert from_dict(m.to_dict()) == m
  # 变体：逐字段点名报差异，避免 assert 只给一句"不相等"
  ```
  新字段漏写 `from_dict` 立刻红，不依赖有人想到补业务测试。
- **`except` 里必须带 `traceback.format_exc()`**，不能只记 `str(exc)`。
- **自校验抛出的异常不允许被宽泛 except 吞**：要么窄化范围，要么把校验结果单独上报，
  不能和「磁盘满了」混为一谈。

## 2. ★ 门禁自身的两种假信号：「没触发」可能是「没运行」

**现象**（同一天连踩两次）：
- 造了个探针验证「pytest 会不会写进仓库」，结果**没触发**，差点判「门禁无效」。
  真相：探针文件写在**仓库根**，而 `conftest.py` 在 `tests/` —— **压根没被加载**。
  「没触发」实际是「**没运行**」。
- 改对目录后仍然没触发。这次探针走了 `save_record`，被第一道防线（路径隔离）
  导去了 tmp，**根本没触发到第二道**。差点把「第一道有效」误判成「两道都无效」。

**根因**：`0 条命中` 与 `0 条检查` 长得一模一样。门禁自身出错却报成功，
比没有门禁更危险 —— 它会把排查引向错误方向，而且因为"有绿灯"而不再有人复核。

**判定口**
- 门禁报绿/未命中时，先问：**「门禁真的跑了吗」**，再问「它抓不抓得到」。
- 判据优先级必须是 **`工具自身出错 > 测到故障 > 通过`**，
  并且 `total_checks == 0` 一律判 ERROR 而不是 PASS。

**对策**
- **造一个已知违规**（真文件注入变异 / 故意写脏）验证门禁真能报出来，再拿它去测目标。
- 门禁输出里放一个 **ASCII 标记**（如 `[REPO_WRITE_VIOLATION]`），
  不要只用中文 —— 跨编码环境会因乱码导致子串匹配假阴性。

## 3. 双层防线：第一道按路径拦，第二道按效果判

**现象**：某测试收了 `monkeypatch` 参数**却一次都没用过**，
`open(p, "w")` 把生产取证文件（991 行真机数据）**截断覆盖成 41 行测试数据**。
根因是框架层 fixture 隔离了 `a.app_root`、`b.tracer`，**唯独漏了 `c.app_root`** ——
而默认落点正是从 `c` 派生的。

**判定口**：只修当前报错的调用点是治标；**框架层缺口会让同类问题无限复发**。

**对策**
| 层 | 做法 | 性质 |
|---|---|---|
| ① 路径隔离 | fixture 里把所有**派生根**一并重定向到 tmp | 按路径拦，快 |
| ② 会话守卫 | session 级前后比对受保护目录指纹（文件数/总字节/最新 mtime_ns），变了报红 | 按效果判，不关心是谁写的 |

两道**独立**，任一失效都还有另一道。第二道必须活到 session 结束 ——
单测内的断言看不见别的测试写了什么。

★ 枚举派生根时按**「谁还从 app_root 派生」**列全，不要只补当前报错的那个。
★ 守卫要留 `ENV=off` 开关：**一个关不掉的守卫等于一个没法调试的守卫**。

## 4. ★「已知问题」标签会掩盖真根因

**现象**：某测试段连续三轮稳定在 240 s 超时，一律被记为
「已知 Qt 测试间相互干扰（30 文件单跑全通过，合在一起才超时）」。

**判定口**：**每次都被解释成环境噪声，就没人问「为什么 REALLY 值得追」。**
「已知/偶发」是最容易长期存活的错误结论。

**对策**
- 任何被标为「已知 / 环境噪声 / 偶发」的现象，写下**下一次复查的触发条件**。
- 有可疑机制时（共享目录、共享端口、共享全局状态、后台线程）优先查机制，别先接受标签。

### 4.1 ★「单跑通过」不能证明「不是它的问题」

**现象**：同一个 240 s 超时被「30 文件逐个单跑全部通过」结案了**至少三轮**。
真实原因是某个测试文件**间歇性挂死** —— 独立重复 6 轮里**挂了 2 轮**，
而每次复核都恰好落在通过的轮次上。

**判定口**
- **间歇性现象不能用单次观测结案。**「单跑通过」只说明**这一轮**通过。
- 「某现象在一次改动后消失」**不能证明**该改动是原因 ——
  尤其当现象本身就是间歇的。
  **一次观测只能支持「可能相关」，不能支持「因此」。**

**对策**
- 间歇性缺陷**必须用重复跑定位命中率**（N 轮挂 k 次），拿到 k/N 才有资格
  说「可复现」，也才有资格用抓栈工具。
- 抓挂死栈的**零依赖手段**（Windows/Linux 都可用，比装 py-spy / pytest-timeout 轻）：
  ```python
  import faulthandler
  with open("hang.txt", "w", encoding="utf-8") as fh:
      faulthandler.enable(file=fh)
      faulthandler.dump_traceback_later(25, exit=True, file=fh)   # 25s 未结束就 dump 并退出
      pytest.main([...])
  ```
  它给出**全部线程**栈 —— 单线程栈看不出「谁在抢 GIL」。

## 4b. ★ 循环空转：线程还活着 ≠ 线程在干活

**现象**：`conn_manager._reader_loop` 的退出条件只看 `stop_event`，而 `self._device`
可被**非异常路径**（写失败触发的 `_handle_link_lost`）置空却**不换 `_stop`**
⇒ 循环条件恒真、循环体在 `_pump_once` 的早退分支里恒空
⇒ **100% CPU 热自旋**。

实测（修复前）：`device=None` 期间 **0.516 s CPU / 0.518 s 墙钟 = 99.5%**。

**为什么这在产线上很严重**
1. 该线程是 **daemon 且永不退出** ⇒ 进程活着就一直烧一个核；
2. 与**采样/IO 线程争 GIL** ⇒ 表现为「莫名其妙的数据流空洞」，
   与「通信架构有问题」的错误归因高度重合（本项目就曾把 DEC-392/400 的空洞
   一度归到 RS485 上）；
3. **它不报错、不告警、不写日志** —— 最阴的一类缺陷。

**判定口**
- 怀疑循环空转时，**不要只看线程是否存活**（活着可能只是慢）。
  要量 **CPU 占比**：
  ```python
  cpu = time.process_time() - t0; wall = time.monotonic() - t0
  assert cpu < wall * 0.35        # 自旋时该比值 ≈ 1.0
  ```
- **门禁里必须有这条 CPU 度量断言**，否则「线程没退出」测不出「它在空转」。

**对策**
- 循环退出条件要覆盖**它依赖的全部状态**，不只是停止标志。
  典型：读循环还要看 `device is None` —— 没有设备可读时，退出是唯一正确行为
  （重连会开**新**线程，旧线程留着空转毫无意义）。
- 改线程循环条件时**必须配反向门禁**：正常路径（有设备时线程必须仍活着），
  防止条件写过头导致「该跑的也不跑」。

## 4c. ★「加了门禁就出问题」→ 先 A/B，再量化门禁自身开销

**现象**：A/B 实测 —— 会话守卫**关** 0/8 挂死、**开** 6/8 挂死。
直觉会指向「守卫引入了问题」。

**真相**：量化守卫自身耗时仅 **0.08 s**。它没制造问题，只是**给了被饿死的主线程
一份 1.2 万文件的遍历活儿**，让饿死从「看不见」变成「看得见」。
修掉真正的自旋后：A/B **16 轮全过**，且耗时从「1.5 / 9.5 / 9.2 s 抖动」
收敛到**稳定 1.5 s** —— 证明自旋原本两边都在，门禁只是放大器。

**判定口**：**新加的东西一出问题就出事，先当它是显影剂，不是原因。**

**对策**
1. **A/B 对照**（有/无该组件各 N 轮，数命中率）；
2. **量化它自身的开销**（单独计时）；
3. 两者合起来才能区分「原因」与「显影剂」。

## 5. ★ 假前提被编进注释和测试，而测试自己会喊

**现象**：注释与测试都断言「AD→g 分段非线性，AD 越大反而 g 更小」，
并配了两个常量。实测生产数据 `corr = 1.000000`（严格单调）——
**该前提从写下那天起就没成立过**。

**关键**：那条测试**自带的鉴别力守卫**（`pytest.fail("本用例失去鉴别力")`）
**第一次运行就报了红**。信息一直在那儿，只是当时没去核。

**判定口**：**测试自带的「失去鉴别力」守卫当场报红 = 前提是编的，不是测试坏了。**
把这类守卫当**事实核查信号**读。

**对策**
- 先回生产数据核事实，再决定改测试还是改实现 —— 不要直接改断言让它绿。
- 需要反例时用**显式构造的合成数据**（如刻意的非线性标定），
  并**写清「合成，不代表真机」**；同时另加一条测试把**实测事实**钉死。
- 反过来：口径本身正确的实现可以保留（如「按物理量而非原始 ADC 值比较」），
  它不依赖单调性假设，零成本且更稳健 —— **不要因为前提被推翻就连实现一起删**。

## 6. 数据形态不匹配时，用公式反推会给出无意义结果

**现象**：想从记录的力上升率反推 Z 逼近速度（`dF/dt = k·v`），
算出来 p50 = **0.0000 mm/s**。原因是该记录的 Fz 是 **1.75 s 渐进上升**
（板端下压阶段），**不是一次干净的接触冲击**，该公式的适用前提不成立。

**判定口**：**用公式反推之前，先确认数据形态符合公式的前提。**
p50 恰好等于 0 是强烈信号 —— 通常意味着「大部分样本里自变量没变」。

**对策**：权威值优先从**控制流元数据**取（本例：trace 里的
`init_start home_speed_steps = -768`），而不是从响应曲线反推。
trace 里的**下发值**是因果链上游，反推值只是下游推论。

## 7. 冻结指纹类门禁的价值，以及正确的处置顺序

**现象**：改动一个登记在案的魔数后，门禁如期报漂移。

**判定口**：门禁**如期**报漂移 ⇒ **门禁有效**（不是"要绕过它"）。

**对策顺序**（登记先行的完整闭环）
1. 先查该常量在**全仓的每一处引用** —— 常量很少只出现在一处
   （本例：常量 + 登记指纹 + 测试期望 + 6 处文案 + 3 个探针脚本）；
2. 写 DEC 说明**为什么**改、逻辑校验是什么；
3. 跑测试验证；
4. 按门禁提示重生成基线；
5. 再跑一次确认回绿。

## 7b. ★★★ 排查「东西没画出来/没生效」的三条铁律（2026-10-13 实战产出）

本节三条来自一次**真实且昂贵**的排查：曲线在数据完好、视图正确、笔刷正常、
场景归属正确、离屏环境正常、Qt 主题全部无害的条件下**就是不画**。
前六条怀疑全是死路，真根因是「**还有谁在改写这块数据**」。

### 7b.1 顺着「谁在改写数据」倒查，比顺着渲染链往上找快得多

**现象**：图层里数据齐全却不显示。
我先后排除了：数据缺失 / 视图范围 / 抽稀 / 笔刷 / 场景归属 / 离屏环境 / Qt 主题 —— **七条全是死路**。
真根因：另一个**周期性回调**也在往同一块数据 `set_data(...)`，把结果覆盖了
（未连接时是空缓冲，生产时是实时滚动窗 —— 两条分支撞同一个失效条件）。

**判定口**
> **`0 条命中` 与 `0 条检查` 长得一模一样。**
> 排除法穷尽后，**必须回头问「还有什么在写它 / 还有什么会改它」**，
> 而不是继续在那条链上翻。

**做法**
- 倒着查：**谁持有这块状态、谁调它的写方法**。grep 写方法的**调用点**，
  而不是查被写对象的属性。
- 特别注意 **UI 的两条并行数据流**：「实时采集」与「历史回放」共用同一个绘制对象时，
  实时流若不知道回放态存在，就会持续覆盖。

### 7b.2 「上层对象可见」≠「真正绘制的东西可见」

`item.isVisible() == True` 骗了我很久。真凶在**子项**：`item.curve.isVisible() == False`。

**Qt/QGraphics 的可见性是逐 item 生效的**：代理/包装对象的状态不代表子项。
**排查渲染问题要一路问到叶子**（被 hide 的常常是内部 child，不是你拿到的那个对象）。

### 7b.3 对照实验必须走**同一条代码通路**

我做过一次无效对照：实验组用 `wrapper.setData(...)`（触发内部刷新分支），
对照组用 `inner.setData(...)`（**绕过**那个分支）。据此得出的
「关了某开关还是不行」**整整错了一轮排查**。

**判定口**
> **对照组和实验组差了什么，必须逐行写下来再跑。**
> 只要差了一条内部通路，结论就不成立。

**配套**：抓栈优先用零依赖手段
```python
faulthandler.dump_traceback_later(25, exit=True, file=fh)
```
它给出**全部线程**栈 —— 单线程栈看不出「谁在抢 GIL / 谁在空转」。

### 7b.4 离线复现必须覆盖「现场有、我没有」的条件

离线走 A 分支、现场走 B 分支，若两者撞同一个失效条件，则**同一处修复同时覆盖**；
若不撞，就会被误判成「现场是另一个问题」。

**做法**：先问「现场的运行环境多了什么」（连接状态、定时器、后台任务、数据量），
**把那些条件补进离线复现**，再开始排查。

## 8. 跨平台执行环境：三个反复踩的坑

### 8.1 Windows PowerShell 会吃掉内联脚本里的引号

**现象**：`.venv/Scripts/python.exe -c "...<多行内容含 \" 和 ' >..."`
反复报 `ParserError` 或 `SyntaxError: unterminated triple-quoted string literal`。

**对策**：**多行 / 含引号的脚本一律 `write` 落文件再执行**，不要用 `python -c`。
这条在 bash 下也适用（多层引号转义同样脆弱），属于通用纪律。

### 8.2 Windows 控制台默认 GBK，诊断脚本会把自己打断

**现象**：探针脚本打印 pytest 输出（含替换字符）时抛
`UnicodeEncodeError: 'gbk' codec can't encode ...`，**脚本自己崩了**，
退出码却看起来像"检测失败"。

**判定口**：诊断工具自身崩溃 ⇒ 它给出的任何结论都不可信。

**对策**：脚本第一行固定
```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

### 8.3 后台任务的输出可能被截断，汇总不能替代逐项

**现象**：分段测试 runner 的逐项结论**输出开头被工具截断**，
汇总行却显示全部通过。若直接采信汇总就是**交付未验证的结论**。

**判定口**：**任务状态是「我提交了什么」的记录，不是「系统里还有什么」的真相。**
同理，**runner 的汇总绿 ≠ 每个子项都绿**。

**对策**
- 汇总结论被截断/可疑时，**自己重跑一遍**并只报失败项（成本远低于返工）。
- 打包产物（onefile EXE）内部是压缩的，**裸 grep 搜不到版本号**；
  用归档读取器解出模块 code object 再取常量，才算真核验过包内代码。
- 收尾固定看**进程表**判断有无孤儿，不看任务状态。

## 9. 收尾扫一眼工作树：能发现整类静默破坏

**现象**：`git status` 里一个取证文件从 991 行变成 41 行 —— 不是新增，是被覆盖。
是「测试写进真实目录」这类问题唯一的发现入口。

**判定口**：**收尾不看工作树，等于没收尾。**
「我只改了 X」这种自我认知不可信，diff 才是。

**对策**：每次交付固定跑一次 `git status --porcelain`，
对每个意外改动逐个判定「是我的吗 / 能恢复吗 / 该不该恢复」。
取证文件优先从版本控制恢复，**不按文件名猜测删除**。

★ **别急着报警**：本例进一步查到「35,416 → 991」其实是**两次不同真机 run 的先后覆盖**，
不是数据丢失 —— 原始证据在另一个路径下完好。
**先查清三份文件各自是什么，再下结论。**

## 10. 改完要「独立复现」，不能采信工具的汇总

**现象**：工具/脚本报告「已验证 / 全绿 / 通过」，但输出可能被截断、
可能用的是自己的缓存、可能自身出错。

**判定口**：**交付前对关键结论独立复现一次**；
**工具说它做了 ≠ 它真的做了**。

**对策**
- 关键指标用**两种方式**各测一次（如 runner 汇总 + 逐项复核）。
- 产物类结论同时看**属性**（mtime/size/hash）与**内容**（包内 code object）。
- 脚本类结论留**可重跑的最小复现**，别只留一句"我验证过了"。
